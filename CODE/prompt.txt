### The Real Bug — Bad Calibration Offset at Boot

Look at `setup()`:
```
Line 1897: calibrateMPU();   ← runs during boot, takes ~900ms (300 × 3ms)
Line 1901: WiFi.begin(...)   ← WiFi stack starts
...
Line 1931: lastSampleUs = micros();  ← only set AFTER all setup is done (could be 10+ seconds later)
```

The **calibration runs during boot while Wi-Fi hasn't started yet** — so the board is completely cold. When the robot is picked up, placed on the table, or even breathed on during that 900ms window, the measured offset is **wrong**.

The result: `gyroZ_offset` is miscalibrated by e.g. `0.09 rad/s` = `5°/s`. The deadband only filters `gz < 0.6°/s`. So **5°/s leaks through every loop**, accumulating 300°/minute → **2700° in 9 minutes**. Matches exactly what you see.

Also notice: **`reset_yaw` only zeroes `currentYaw` — it does NOT re-run calibration or fix the bad offset.** So after you press reset, the wrong offset keeps pumping yaw upward from zero.

---

### The Fix

Three changes to [`esp_main.ino`](file:///c:/Users/Jeremy/Desktop/SCHOOL%20ACTIVITIES/500%20level/Final_Year_Project/Auto_Waste_Bin/CODE/TEST_WEB_Scrap/esp_main/esp_main.ino):

1. **`calibrateMPU()`** — add a stability variance check. If the sensor was moving during calibration, the samples will have high variance → reject and retry.
2. **`reset_yaw` API handler** — re-run calibration (with the robot now fully warmed up and stationary) instead of just zeroing `currentYaw`.
3. **`updateMPU()`** — clamp `dt` to max 50ms to prevent any startup spike.
